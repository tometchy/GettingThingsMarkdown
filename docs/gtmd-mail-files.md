# File-based mail ingress and zero standing privileges

The native Syncthing receiveencrypted folder must NOT be written to using an arbitrary public-key cipher. Syncthing expects its own encrypted names, block metadata and password-derived file keys. The existing notes folder remains receiveencrypted, and no server gets its password.

The encrypted mail transport is a separate ciphertext-only working directory, /data/mail/.gtmd/inbox, on the SAME Sync PVC. Git stores it on an append-only gtm-mail branch in the SAME native Git repository (no extra per-tenant container or database). SMTP success in Kubernetes requires the tenant's Sync worker to commit and push the envelope to History first. Git retries are idempotent by message digest. No automatic history deletion. The HTTP client delivery/index is a compatibility bridge for older clients. With native mailbox pairing, the client scans the synced .gtmd/inbox files and imports locally even when the account API is offline; generated Markdown and attachment files travel through normal E2EE notes sync. Native mailbox transport uses a distinct Syncthing peer identity in the same Sync container for Plus/Pro, sendonly on port 22001; the trusted client receives the already-encrypted files in .gtmd/inbox while the primary E2EE notes folder ignores that nested transport folder. No additional tenant container. The HTTP path remains a compatibility bridge for earlier clients.

The original MIME data and attachments must never be discarded merely because the Markdown rendering cannot display them. Files are saved on trusted clients; remote images must not be fetched automatically. Multiple per-device public keys wrap one content encryption key. A later-added key cannot decrypt already-existing envelopes without rewrapping by a previously authorized device. Existing key backups still matter.

Production access model: no standing human SSH or Kubernetes administrative credentials. Private worker IPs; no public bastion; deploy via narrowly scoped workload identity and observe via read-only metrics. Cloud organization owner can explicitly escalate through provider IAM (break-glass, MFA, audit), which is outside the normal operator role. A private IP alone is not IAM isolation. Production network/IAM verification must include provider console access, SSH, Kubernetes exec/attach/port-forward/secrets, and CI credentials. No actual cloud resources provisioned in this PR.

Remaining gates: actual independent provider IAM and no-standing-access tests, end-to-end native mailbox Syncthing transport validation, restoration of encrypted mailbox registry into the control-plane DB and automatic cloud failover, mobile apps, history erasure/immutable retention and hard quota enforcement. Mailbox settings (alias, account ID, registered public keys, enabled flag) are saved as .gtmd/settings.json.age in both Git copies when independent age recovery recipients are configured; no private device keys are included. The SQLite delivery index still exists and needs a Git-driven rebuild; new Kubernetes deliveries store only metadata there, not the ciphertext. It is not the authoritative durable byte store. Existing legacy rows are retained without automatic expiry. The MIME envelope limit is 40 MiB raw SMTP; exceeding the limit is explicitly rejected, never accepted with stripped attachments. Each API response carries at most one envelope to bound memory. In development without Kubernetes, the legacy SQLite fallback is for unit testing only.

The Scaleway IAM module creates a project-scoped observability-only group with no users by default. Supply IDs of distinct day-to-day operator accounts in observability_operator_user_ids. IAM policies are additive: these users must not have other elevated policies. Never use the organization-owner account for daily operation. Keep its credentials protected separately; bootstrap and incident recovery require an explicit privileged change. Verify actual denied access before accepting production.
