# E-mail forwarding → encrypted queue → trusted-client Markdown tasks

Status: **engineering preview; no public MX or production SMTP service deployed**.
New feature is available only to an entitled and verified **Plus** or **Pro** account, including an eligible trial. **Mini** receives HTTP 403.

## Security: why the SMTP server cannot upload directly to Syncthing E2EE

An untrusted Syncthing device is a **Receive Encrypted** replica. Its encrypted on-disk representation and metadata cannot be generated by a generic public-key encryptor. Only an authorized trusted Syncthing device with the folder's encryption password knows how to create that representation.

We deliberately keep the SMTP gateway entirely separate from this password:

1. A trusted desktop creates a new **RSA 3072-bit public/private key pair** for the mailbox. The private key is in the device's private app profile and can be exported to a second trusted device. **Never send it to a server or paste it into the website.**
2. The account registers only RSA SPKI public bytes. The server generates a cryptographically random **192-bit alias** `r<48 hex chars>@inbox.example.com`.
3. Gmail/Outlook/etc. forward NEW emails to the MX for that domain. An authenticated gateway briefly receives plaintext SMTP DATA and hands it to the internal Control Plane. Sender-domain TLS and STARTTLS (when negotiated) protect transport only; incoming SMTP is not guaranteed to use TLS end-to-end. A self-hosted SMTP server cannot honestly claim sender-side E2EE of messages forwarded from Gmail.
4. Control Plane parses MIME, prefers text/plain and converts HTML-only messages to inert text with URLs; attachments are deliberately **ignored**. It generates AES-256-GCM key/nonce and encrypts a canonical JSON task. The AES key is wrapped with **RSA-OAEP-SHA256** using the account public key. SQLite stores only encrypted payload + opaque metadata, never plaintext mail or the private key.
5. The gateway only returns successful SMTP delivery if the encrypted SQLite transaction succeeds. Failed persistence returns temporary failure, allowing retries. Duplicate MIME bytes are deduplicated. Messages are limited to **256 KiB raw**, **200 pending per account**, **100 received in the last day** (in addition to the SMTP server's size check).
6. An authenticated, **trusted** desktop downloads ciphertext, decrypts with the private mailbox key locally, atomically writes `ToDo/mail-<id>.md` and ACKs only after successful local write. **ACK is non-destructive**: ciphertext remains available in the user's archive for 30 days after ACK, extended by tenant-wide incident holds. Unacknowledged messages are never expired automatically. An existing file is not overwritten on retry. Background polling occurs every 60 seconds while the desktop app is open and a local workspace folder is selected.
7. Syncthing then synchronizes the new Markdown file with the same encrypted-untrusted-device behavior as all ordinary user tasks. The mail gateway does not need the Syncthing symmetric key or account's local Markdown.

**Critical limits:** This protects queued mail against ordinary disk disclosure. It does **not** protect email content from a compromised SMTP process while it is transiently plaintext. It also does not prevent malicious clients with control-plane administrative privileges from tampering with an account's public key before registration. Cloud root/security separation, queue replication and incident response require additional infrastructure and tests.

## Workflow

Use the native desktop GUI with the existing Plus/Pro account, pair a trusted Syncthing folder and click **Create encrypted mail forwarding address**. Copy the generated address and register it in Gmail: Settings → See all settings → Forwarding and POP/IMAP → Add a forwarding address. Gmail sends a confirmation email. Click **Import pending mail to local ToDo** to read the confirmation link. Approve forwarding in Gmail and enable forwarding of incoming messages. The importer adds emails to `ToDo/` when the app is running. If the device is offline, the encrypted queue retains new mail until the next import. After importing, **Restore encrypted inbox archive (30 days)** can re-create missing local `ToDo/` entries after losing a device or folder; it never overwrites existing tasks. A trusted-device copy of the private RSA key is essential for recovery.

For an address leak or abuse, use **Rotate forwarding address** (enter account password again). Old address stops accepting new messages; existing encrypted messages remain pending.

**Back up the mailbox private key on a second trusted device**. Losing every copy of that key loses the ability to decrypt already queued mail. Changing the account password does not recover a lost private key. SMTP does not fetch past Gmail email; only emails forwarded after configuration arrive.

## Development on Linux Mint

Requires Podman rootless, kind, kubectl and existing `./dev.sh up`:

```bash
./dev.sh up
./dev.sh mail-up
# Start native desktop with the folder already paired to Syncthing:
./dev.sh desktop
```

The development SMTP server binds **127.0.0.1:2525**, uses `inbox.test.invalid`, a self-signed STARTTLS certificate, a dedicated randomly generated ingress token in Kubernetes Secret, and a loopback-only `kubectl port-forward`. This is **not** a publicly reachable real email destination. Send a test message with an SMTP test client to `127.0.0.1:2525`, not with Gmail until production MX exists. `./dev.sh mail-down` stops only the SMTP port-forward; it preserves the encrypted queue and pods.

## Production rollout gate (NOT DONE)

- Create a domain such as `inbox.yourdomain.tld`, DNS A/AAAA and MX to a public, dedicated SMTP endpoint on **port 25**. Configure valid public CA TLS certificate and continuously test renewal, IPv4/IPv6, DNS/MX, STARTTLS policy, SPF/DMARC behavior for forwarded messages, and external Gmail forward verification.
- Deploy the shared SMTP Helm service via `mailIngress.enabled=true`, `mailIngress.domain`, `mailIngress.tlsSecret`, `mailIngress.tokenSecret`; only the mail gateway gets the ingress token, which is **not** an admin token. Configure rate limiting at edge/network layer, IP abuse/spam/denial-of-service protection, proxy/ingress restrictions and private internal API. Current `/internal/mail` endpoints are only protected by a shared token; production must additionally enforce network-layer isolation and separate workloads.
- Protect and replicate the Control Plane SQLite account/mail queue/7-day hold/Stripe state across two independent clouds; ensure this mail queue never runs on a standalone, unbacked PVC. Customer emails are encrypted, but loss of the sole SQLite disk still permanently loses pending mail. Provide durable retries and monitoring of failed delivery, queue age and volume.
- SMTP checks the recipient in the Control Plane during `RCPT TO` and rejects nonexistent aliases; add targeted abuse/availability tests, recipient-lookup timeout benchmarks, and external Gmail forwarding consent verification without leaking addresses into public logs.
- Add verified abuse policy, configurable E2EE ciphertext retention, structured observability free of plaintext/sender IDs, account recovery, stable desktop polling lifecycle and fully tested mobile iOS/Android import (background on iOS is constrained).
- Existing history/retention guarantees are **not production-ready**: two Git replicas and 7-day intent do not by themselves offer administrator-proof immutability or automatic physical erasure. The same is true of automatic two-cloud promotion; fencing/quorum, bootstrapping and actual provider fault-injection tests remain required.

Mail limits are temporary prototype boundaries, not published contracted SLA. The encrypted inbox also caps total retained messages at 3000 per tenant and rejects new delivery rather than silently discarding archived or unacknowledged ciphertext when full. The shared background cleanup removes **only acknowledged** messages at least 30 days old and only after the incident hold ends. This window is **not** a proof that Syncthing/Git replication succeeded, and does not survive loss of the single Control Plane PVC. The implementation does not enable generic outbound SMTP or an open relay. Only new inbound email to generated aliases is intended.
