# GettingThingsMarkdown — obowiązująca specyfikacja MVP i instrukcja kontynuacji

Aktualizacja: 2026-11-26. Repozytorium: https://github.com/tometchy/GettingThingsMarkdown

## 1. Jak korzystać z tej specyfikacji
Kontynuuj implementację istniejącego GTMD, nie zaczynaj od nowa. Najpierw sprawdź main, PR-y, CI, kod i dokumentację. Ten dokument jest nadrzędną specyfikacją produktu i planem prac; w razie sprzeczności z wcześniejszą dokumentacją obowiązuje on. Aktualizuj go po nowych ustaleniach. Zapisuj rzeczywisty stan realizacji i wyniki testów w docs/mvp-acceptance.md. Pracuj bezpośrednio w repozytorium, dostarczaj kod, konfigurację, testy i PR-y; nie ograniczaj się do planów ani pustych interfejsów.
Projekt nie ma jeszcze rzeczywistych użytkowników ani danych produkcyjnych. Nie projektuj migracji kont, abonamentów, maili, istniejących wolumenów, kluczy ani repozytoriów LFS. Usuń niepotrzebne ścieżki zgodności ze starym prototypem zamiast budować migratory. Można odtworzyć jednorazowe środowisko deweloperskie i dane testowe; nie kasuj cudzych danych ani zasobów bez upoważnienia. Zachowaj działające funkcje i testy.
Nie wdrażaj płatnych zasobów bez zgody. Testuj lokalnie, w CI, emulatorach i środowiskach tymczasowych. Nie twierdź, że coś działa produkcyjnie na podstawie samego zielonego CI. Raportuj wykonane zmiany, testy, blokery, nierozwiązane ryzyka i decyzje wymagające zgody.

## 2. Produkt i środowisko
- 100% open source; backend C#/.NET, klient Avalonia, lokalne pliki Markdown, automatyzacje GTD (w tym archiwizacja zakończonych zadań), zadania, załączniki, edycja i podgląd.
- Jeden zintegrowany klient: Linux x86-64 i ARM64 (Flatpak, m.in. ThinkPad X13s Ubuntu i Linux Mint), Windows, Android i iOS. Pełna funkcjonalność na mobilnych i desktopowych platformach: synchronizacja, poczta, historia, odzyskiwanie, sprzątanie, konto, zakup i zarządzanie abonamentem, klucze. Użytkownik nie instaluje ręcznie Syncthing, nie używa terminala, SSH, Termuxa ani Pythona. Opcjonalny zaawansowany panel Syncthing.
- **Jeden wspólny kod aplikacji Avalonia dla Android, iOS, Windows, Linux i WWW (WASM)**: wspólne widoki, view models, logika domenowa, API, lokalizacja, konta, pełne zarządzanie abonamentem i płatnościami, historia, podgląd, odzyskiwanie i kryptografia tam, gdzie technicznie możliwe. Nie twórz osobnego portalu tylko dlatego, że funkcja dotyczy konta lub płatności. Oddzielaj wyłącznie niezbędne adaptery platformowe (Syncthing, filesystem, keystore, PRF, powiadomienia, billing). Na webie pomiń wyłącznie funkcje rzeczywiście niewykonalne lub nieproporcjonalnie trudne, przede wszystkim ciągłą synchronizację natywnego Syncthing; pobieranie zaszyfrowanych wersji z Git, lokalne odszyfrowywanie, podgląd i eksport realizuj również w WASM, jeśli bezpiecznie wykonalne. Nie przekazuj kluczy backendowi. Pokaż macierz dostępności i uzasadnij wyjątki; nie ukrywaj funkcji tylko z powodu platformy. Użytkownik każdej aplikacji musi móc zmienić kartę, plan, anulować i zarządzać płatnościami bez osobnego logowania do webowego portalu GTMD; dopuszczalny autoryzowany system browser/Stripe Customer Portal lub natywna obsługa sklepu, bez ponownego logowania GTMD i z bezpiecznym powrotem.
- Development Linux Mint, kind na rootless Podman; CI może używać Docker/kind. Produkcyjnie Kubernetes, Terraform/OpenTofu, automatyczne skalowanie, małe koszty bez osłabiania bezpieczeństwa.
- Dwa stale działające kontenery danych na klienta; współdzielone usługi nie są kontenerami per klient.
- Android: jako wzorzec integracji Syncthing przeanalizuj https://github.com/chenxiaolong/BasicSync (Go/stbridge, AAR, Android SDK/NDK, SAF, foreground service, ograniczenia baterii/sieci, konfiguracja i proces build). Nie wymagaj instalacji BasicSync jako osobnej aplikacji. Sprawdź zgodność licencji: BasicSync GPL-3.0-only, Syncthing MPL-2.0. iOS wymaga właściwego osadzenia natywnego silnika (Go bindings lub równoważne), nie desktopowego uruchamiania procesu; zbadaj działające rozwiązania i ograniczenia sandbox/background. Pełna parytet funkcji jest kryterium MVP; ograniczenia pracy w tle narzucone przez OS jasno komunikuj, zapewnij wznawianie i synchronizację przy otwartej aplikacji. Nie uznawaj mobilnej powłoki bez silnika za ukończoną.
- Angielski i polski w całym produkcie: zasoby lokalizacyjne, domyślnie en, automatyczny wybór systemowy i ręczny przełącznik, kody błędów API, lokalizacja dat/liczb/cen, e-maili, panelu admina, recovery i PDF. CI kontroluje kompletność; nie tłumacz nazw plików ani wartości automatyzacji.

## 3. Dwie chmury i Git jako źródło prawdy
Dwa niezależne cloud providers, docelowo Hetzner i OVH (dobór zweryfikuj ekonomicznie i technicznie).
A: Syncthing receiveencrypted, zaszyfrowany working tree, pełny Git i automatyczny commit/push.
B: Gitea i pełny bare Git. Wewnętrzny SQLite Gitea jest lokalnym stanem odtwarzalnym, nie wykonuj osobnego backupu; odtwórz Gitea, konta techniczne, uprawnienia i certyfikaty z Git oraz konfiguracji. Nie potrzebujemy funkcji Issues/Wiki/PR Gitea.
Jedno logiczne repozytorium Git na klienta, dwie pełne kopie, wszystkie gałęzie w tym samym repozytorium. Nie twórz oddzielnego repo mailowego ani repozytoriów konfiguracji. Żadnego Git LFS, S3 do danych, trzeciej pełnej kopii lub trzeciego stale działającego kontenera danych. Nie utrzymuj trwałej bazy biznesowej ani osobnego backupu klientów; Git jest jedynym trwałym wewnętrznym źródłem prawdy o koncie, konfiguracji, plikach, historii, sejfie, mailach w transporcie, uprawnieniach, limitach, żądaniach purge i hold. Stripe oraz ewentualny sklep mobilny są zewnętrznymi źródłami prawdy o własnych płatnościach.
Współdzielone API (Control Plane), ingress/routing, SMTP, provisioning, obserwowalność i inne wymagane usługi są **redundantne active-active w obu chmurach**, obsługują ruch normalnie w obu lokalizacjach. Nie wolno uzależnić działania całości od pojedynczej chmury. Active-active nie znaczy niezależnych sprzecznych zapisów: koordynuj operacje per tenant, używaj fencing/lease, CAS i idempotencji. Po utracie chmury ocalała obsługuje ruch i automatycznie odtwarza brakujące komponenty. Sekrety globalne i bootstrap dostępne niezależnie od Git klientów, w odrębnych magazynach obu dostawców.

## 4. Jedno repozytorium — gałęzie
- main: zaszyfrowane pliki Syncthing i kompletna historia, jedyny branch danych rozliczanych (plus chronione referencje tych samych danych).
- gtm-tenant: tenant.json.age, pełna konfiguracja i stan klienta.
- gtm-vault: vault.enc, sejf prywatnych kluczy zaszyfrowany wyłącznie dla metod recovery użytkownika.
- gtm-mail: tymczasowy transport zaszyfrowanej poczty, nie archiwum.
Wszystkie wymagane gałęzie replikowane i weryfikowane w obu kopiach. Uprawnienia odseparowane per branch. Nie wykonuj checkout maili lub konfiguracji do working tree Syncthing. Lokalne pomocnicze indeksy Git dla gałęzi są dopuszczalne, ale wszystkie gałęzie i obiekty należą do tego samego repo. Chronić gałęzie i obiekty innych funkcji podczas purge/repack/GC. Rozwiąż konkurencję zapisu, cleanup maili i przepisywania main w jednym repozytorium; nie proponuj rozdzielenia repozytoriów jako obejścia.

## 5. Routing i tożsamość — bez cache kont SQLite
- Logowanie wyłącznie adresem e-mail i hasłem; brak username, brak wymogu Google login. Niezmienialny losowy UUID (Guid) to ID tenanta, repozytorium i tożsamości. Zmiana e-maila, hasła, planu, urządzeń, dostawcy passkeys lub lokalizacji nie zmienia UUID.
- Nie wprowadzaj accounts.sqlite, tenants.sqlite, centralnego rejestru kont, cache kont SQLite, ani skanowania wszystkich Git przy każdym logowaniu. Projektuj deterministyczny routing do tenanta: np. HMAC-SHA256(globalny sekret routingu, kanoniczny e-mail) jako niejawny alias usługi; alias -> niezmienialny UUID przez routowalne zasoby infrastrukturalne (np. Kubernetes Service/DNS, zweryfikuj limity długości etykiet, kolizje, prywatność). Adresy e-mail nie mogą być jawne w nazwach zasobów. HMAC nie jest uwierzytelnieniem. Zdefiniuj kanonizację e-mail bez arbitralnego utożsamiania różnych skrzynek, w tym IDN; nie usuwaj kropek/plusów dla wszystkich domen. Hash nie powinien być publicznym identyfikatorem. Ochrona i rotacja globalnego sekretu, bez utraty routingu.
- Przy rejestracji wyznacz alias, kieruj sprawdzenie do właściwego tenanta jeśli już istnieje. Brak odpowiedzi lub niedostępność jednego clouda nie oznacza wolnego adresu. W obu chmurach użyj atomowej rezerwacji aliasu/unikalności przez niezależny mechanizm koordynacji (CAS/lease, fencing), bez centralnej bazy danych biznesowych. Nie dopuść do dwóch kont dla tego samego kanonicznego e-maila. Zadbaj o weryfikację e-maila, ochronę przed enumeration/rate abuse, timeout rezerwacji i przerwane rejestracje. Tenant UUID jest generowany raz.
- Zmiana e-maila: świeże uwierzytelnienie i potwierdzenie nowego adresu; atomowa rezerwacja nowego aliasu, trwała zmiana w podpisanym tenant.json.age, dual replication, dezaktywacja starego aliasu; odzyskiwanie po przerwaniu. Alias routingowy jest projekcją, nie niezależną prawdą o koncie. Po awarii odbuduj routing z autorytatywnych konfiguracji i zweryfikowanych metadanych koordynacji; nie skanuj repo przy każdym żądaniu.
- SMTP: losowy nieprzewidywalny alias przekierowania, routing bez globalnej bazy (np. uwierzytelniony identyfikator UUID + losowy sekret aliasu w adresie, sprawdzany w konfiguracji tenanta; zweryfikuj długość local-part <=64 oktety, prywatność, rotację). Stripe: wiąż UUID w zaufanych metadata i zweryfikuj własność zdarzenia. Routing nie może pozwolić na podszywanie się pod innego klienta. Użytkownik nie loguje się technicznymi kontami Gitea.
- Współdzielone mechanizmy koordynacji i service discovery mogą zawierać minimalne metadane routingu, rezerwacje unikalności, wersje i fencing tokeny. Nie są bazą kont ani dodatkowym magazynem danych klienta. Ich odbudowa, dostępność i bezpieczne rozstrzyganie sprzecznych projekcji są obowiązkowe. Nie myl deterministic HMAC z mechanizmem rozstrzygającym unikalność.

## 6. tenant.json.age i uprawnienia
JSON (nie SQLCipher) szyfrowany age dla niezależnych odbiorców infrastruktury. Jeden wersjonowany dokument: UUID, e-mail i hash hasła, weryfikacja, trial, plan, zniżki, limity i granty, stan płatności/Stripe i identyfikatory, konfiguracja Syncthing (cert/key serwera, urządzenia, folder), Gitea (techniczne konta, role), TLS, API, routing i provisioning, alias SMTP i publiczne klucze, żądania purge/hold/cancel, audyt i niezbędny stan idempotencji oraz wszystko potrzebne do odtworzenia tenanta. Nie umieszczaj prywatnych kluczy użytkownika ani hasła szyfrowania folderu Syncthing.
- Podpis cyfrowy zaufanej usługi, kanoniczna serializacja/wersjonowanie schematu, monotoniczna wersja, CAS/lease, autoryzacja operacji, bezpieczny hash hasła. Ochrona przed rollbackiem także gdy całe repo zostało cofnięte: niezależnie chroniony ostatni zatwierdzony hash/wersja w mechanizmie koordynacji.
- Potwierdzaj krytyczne operacje dopiero po trwałym zapisie i dual replication; zaprojektuj protokół rozstrzygania częściowego zapisu w jednej chmurze, retry, fencing, publikację i widoczność zatwierdzonej wersji. W razie utraty jednej repliki nie osłabiaj gwarancji po cichu; określ dostępność odczytu i warunki wstrzymania krytycznych zmian do odzyskania bezpiecznej redundancji.
- Terraform zarządza IAM, tożsamościami usług, odwołaniami do sekretów i uprawnieniami podpisu/decrypt. Publiczne klucze age wewnętrzne, ale nie traktuj tajności klucza publicznego jako zabezpieczenia. Prywatne klucze nie trafiają do IaC/state/logów; użyj niezależnych KMS/secret stores. Zwykły administrator nie ma ich odczytu, jedynie autoryzowane operacje panelu. Globalne sekrety (routing, JWT, płatności, podpis, odzyskiwanie, bootstrap) dostępne niezależnie w obu chmurach. Nie dodawaj backupu bazy kont.

## 7. E2EE, sejf i recovery
Natywny Syncthing receiveencrypted: SaaS nie zna hasła folderu ani prywatnych kluczy użytkownika; zaszyfrowane nazwy i treści, metadata leak (rozmiary, daty) dokumentuj. Klucze infrastruktury i użytkownika są niezależne. Losowe klucze generowane lokalnie, niezależnie od hasła logowania. Sejf w gtm-vault (obie repliki) zawiera klucze Syncthing, poczty i poprzednie generacje; losowy klucz sejfu, AEAD, envelope encryption, dla każdej metody recovery osobno zabezpieczona kopia klucza sejfu. Dodanie metody nie wymaga ponownego szyfrowania wszystkich plików. Integralność, wersjonowanie, ochrona przed rollbackiem i konfliktami urządzeń, zabezpieczenie przed podmianą publicznych kluczy, autoryzowany transfer zaufania. Nie wysyłaj sekretów do backendu, logów ani telemetrii.
Metody recovery:
1. Zaufane urządzenie: uwierzytelniony transfer (ochrona MITM), autoryzacja nowego urządzenia.
2. **Obowiązkowy dla każdego konta losowy klucz recovery o wysokiej entropii:** lokalnie generowany PDF do wydruku, czytelny kod, opcjonalny QR i instrukcja PL/EN. Alternatywnie **menedżer haseł z niezależnym odzyskiwaniem / synchronizacją online** (np. Bitwarden/1Password; nie sugeruj wyłącznie lokalnego sejfu na tym samym urządzeniu), niezależny nośnik. PDF i sekret nie opuszczają klienta z wyjątkiem świadomego eksportu do wskazanego miejsca; bez wrażliwych temp/logów. Wyraźne ostrzeżenie o utracie jedynej kopii.
3. Opcjonalne osobne hasło sejfu, Argon2id lub równoważny silny KDF z solą i wersjonowanymi parametrami; nie używaj zwykłego hasła konta jako jedynego zabezpieczenia.
4. Opcjonalne odzyskiwanie przez synchronizowany passkey z WebAuthn PRF jako dodatkowa wygodna metoda, nigdy zamiennik obowiązkowego niezależnego klucza recovery.
Przed rozpoczęciem synchronizacji lub zapisem pierwszych danych użytkownika obowiązkowy onboarding recovery: wygeneruj lokalnie niezależny losowy klucz recovery i zaszyfruj nim kopię klucza sejfu. Wymagaj świadomego eksportu PDF/kodu, wydruku lub zapisu w niezależnym menedżerze haseł online (dostępnym po utracie urządzenia). Nie pozwalaj ukończyć onboardingu samym passkey, zaufanym urządzeniem lub zapamiętanym hasłem. Jasno wyjaśnij PL/EN, że GTMD nie zna kluczy, utrata urządzeń i wszystkich metod recovery oznacza nieodwracalną utratę dostępu, a jedyna kopia w GTMD (w tym jego synchronizowany folder) lub na tym samym urządzeniu jest niedopuszczalna. Wyświetl wyraźne ostrzeżenie w onboardingu, przed eksportem i na PDF/kodzie (PL/EN), np. „Chroń swój klucz odzyskiwania. Pozwala on odszyfrować Twoje prywatne dane. Jeśli trafi w niepowołane ręce, bezpieczeństwo wszystkich Twoich plików może być zagrożone. Przechowuj go bezpiecznie poza GTMD i obecnym urządzeniem. Nie udostępniaj go nikomu, nawet pracownikom GTMD.” Wymagaj potwierdzenia zrozumienia ryzyka. Wyjaśnij w pomocy, że sam klucz nie wystarcza do resetu hasła lub logowania, ale wraz z dostępem do ciphertext/sejfu pozwala odszyfrować dane, również bez serwera. Nie sugeruj, że rozdzielenie logowania usuwa ryzyko kradzieży klucza. Rekomenduj zamknięte bezpieczne miejsce lub niezależny szyfrowany menedżer haseł online; przechwycony PDF jest sekretem wysokiego ryzyka. Ostrzegaj i blokuj eksport do znanego folderu GTMD; nie twierdź, że da się zweryfikować fizyczne miejsce przechowania wydruku lub dowolną zewnętrzną lokalizację. Wymagaj potwierdzenia zrozumienia i niezależnego zapisu, a następnie lokalnego testu poprawności wyeksportowanego klucza (np. ponowne wprowadzenie lub zeskanowanie kodu i rzeczywisty unwrap klucza sejfu), nie samego checkboxa. Nie wyświetlaj ponownie sekretu jako automatycznej odpowiedzi na wyzwanie. Żadnych sekretów lub PDF na backendzie, do logów ani do GTMD workspace. Nie blokuj odzyskiwania istniejących danych ze starszego urządzenia podczas ponownego onboardingu; testuj przerwanie procesu, retry, utratę urządzenia i zapomniane hasło. Po ukończeniu obowiązkowego etapu proponuj opcjonalny WebAuthn PRF i inne dodatkowe metody; rekomenduj dwie niezależne metody, umożliwiaj kontrolę/retest, zastąpienie zgubionego recovery key i aktualizację sejfu z zachowaniem bezpieczeństwa starych wersji. **Odzyskanie konta i odszyfrowanie sejfu są bezwzględnie rozdzielone.** Klucz odzyskiwania (PDF/kod) jest wyłącznie sekretem kryptograficznym do lokalnego unwrap sejfu; nie jest credentialem logowania ani tokenem resetu hasła. Sam klucz nie może uwierzytelniać użytkownika w API, wydawać sesji/JWT, pobierać z serwera zaszyfrowanego sejfu lub Git, resetować hasła, zmieniać adresu e-mail ani parować urządzeń. Reset hasła GTMD wymaga niezależnego dowodu kontroli zweryfikowanej skrzynki e-mail (krótko ważny jednorazowy token wysłany do aktualnego adresu; hash tokena, rate limit, bez enumeration, audyt i powiadomienie, unieważnienie starych sesji, ochrona przed replay). Sam reset konta nie odblokowuje sejfu, nie zastępuje jego kluczy i nie upoważnia do trwałego usunięcia historii. Odróżnij autoryzację konta od zaufania kryptograficznego do nowego urządzenia; dodanie urządzenia i podmiana kluczy wymagają obu. Nie twórz publicznych lub przewidywalnych endpointów pozwalających pobierać ciphertext bez uwierzytelnienia. Utrata jedynego urządzenia i zapomnienie hasła GTMD nie oznaczają utraty danych, jeśli użytkownik odzyska konto (np. przez swój e-mail) i zachował metodę recovery. Jeśli utracił także skrzynkę, nie obiecuj resetu na podstawie samego klucza; zaprojektuj przyszłe niezależne metody odzyskiwania konta lub wyjaśnij ograniczenie. Po utracie wszystkich sekretów nie da się odzyskać danych bez złamania E2EE. Nie obiecuj niemożliwego.
Magazyny systemowe: Android Keystore, iOS Keychain, Windows DPAPI, Linux Secret Service/keyring; bezpieczny fallback. Dodawanie/odwoływanie urządzeń, usuwanie kluczy publicznych, rotacja, dostęp do starszej historii/poczty, odzyskiwanie po utracie. Odwołanie nie odbiera już skopiowanych/odszyfrowanych danych. Nie zmieniaj automatycznie sekretu Syncthing w sposób uniemożliwiający odczyt historii. Przy odwołaniu metody recovery uwzględnij stare wersje sejfu w Git (stare kopie/sekrety mogą nadal odblokowywać stare dane); nie obiecuj skutecznego odwołania kryptograficznego bez odpowiedniego protokołu rotacji i ochrony historii. Dodaj jasny proces zgłoszenia utraty/kradzieży klucza: zabezpieczenie konta, unieważnienie sesji i nieznanych urządzeń, wydanie nowego recovery kit, rotacja klucza sejfu i w razie potrzeby kluczy danych/poczty; opracuj sposób odcięcia starych wrapów w gtm-vault bez naruszenia retencji danych użytkownika. Samo opakowanie tego samego klucza nowym kodem nie odbiera dostępu atakującemu posiadającemu stare wrapy; rotacja nie cofa wcześniejszego ujawnienia ani kopii ciphertextu z kluczem. W razie resetu hasła lub odzyskania konta wprowadź powiadomienia i ochronę przed przejęciem konta i ransomware (np. czasowy hold na destrukcyjne operacje, niezależne potwierdzenie; konkretna polityka do zaprojektowania); nie osłabiaj obowiązkowych 7 dni. Przetestuj, że sam PDF, sam reset konta i sam dostęp do e-maila nie wystarczają do odszyfrowania danych z API, a prawidłowe niezależne odzyskanie konta + klucz działa na czystym urządzeniu.

## 8. Opcjonalne zewnętrzne odzyskiwanie — WebAuthn PRF
Standardowe OIDC/SSO potwierdza tożsamość (iss/sub), nie daje interoperacyjnego prywatnego klucza do odszyfrowania sejfu. Nie używaj ID/access tokenów, publicznych claims, client_secret ani identyfikatora użytkownika jako klucza. Preferuj passkey z rozszerzeniem WebAuthn PRF, które daje lokalnie deterministyczny materiał kryptograficzny dla tego samego poświadczenia i wejścia. Wzorzec działającego produktu: Bitwarden https://contributing.bitwarden.com/architecture/deep-dives/passkeys/implementations/relying-party/prf/ ; standard https://github.com/w3c/webauthn/blob/main/explainers/prf-extension.md .
- Normalne logowanie GTMD nadal e-mail/hasło; passkey dedykowany odzyskiwaniu, nie obowiązkowe SSO ani zamiennik ponownego wpisania hasła przy purge. Użytkownik świadomie rozpoczyna setup/recovery, wybiera dostawcę passkeys w systemowym UI i potwierdza user verification (UV required). Brak automatycznych/background wywołań PRF i dostępu z backendu. Passkey niezależny od poświadczenia do logowania do Google/Microsoft/Apple.
- Wspólna stabilna RP ID/domena, zweryfikowane origins, native app association (Android Digital Asset Links, Apple associated domains), challenge/credential binding i lokalna kryptografia. Losowy salt per credential, domenowo rozdzielony KDF (np. HKDF), AEAD wrap klucza sejfu; w Git tylko publiczne parametry, credential ID, public key, salt, version i wrapped vault key. Wynik PRF/derived key nigdy nie opuszcza zaufanego klienta, także przy serializacji WebAuthn assertion i clientExtensionResults (allowlist zamiast wysyłania pełnego JSON). Nie umieszczaj sekretu w URL, callback, clipboard, logach ani telemetry. Po recovery usuń efemeryczny materiał z pamięci w możliwym zakresie.
- Dostawca synchronizowanych passkeys wybrany przez użytkownika (Google Password Manager, Apple Passwords/iCloud Keychain, Microsoft/Windows lub niezależni dostawcy jak 1Password/Bitwarden wyłącznie gdy konkretna implementacja PRF działa; opcjonalnie fizyczny FIDO2 z hmac-secret). OIDC nie daje dostępu do tych sekretów, a backend nie otrzymuje OAuth tokenów. Nie zakładaj przenośności Windows Hello/device-bound credential ani obsługi PRF przez każdego dostawcę; Google/Microsoft login nie oznacza automatycznie PRF. Użytkownik może potrzebować PIN-u dostawcy lub poprzedniego urządzenia; sama utrata hasła GTMD nie może wykluczać odzyskania przy dostępnej metodzie, ale utrata wszystkich sekretów nadal oznacza utratę danych. Passkey można usunąć, synchronizacja może nie zachować PRF. Zaufanie do klienta/aktualizacji oraz origin webowego pozostaje elementem modelu zagrożeń: złośliwy kod dostarczony przez GTMD mógłby próbować przechwycić lokalny wynik po interakcji. Nie twierdź, że architektura wyklucza złośliwy klient. Chronić dystrybucję i origin, nie dostarczać zdalnie zmiennego kodu kryptograficznego do natywnego recovery; preferuj podpisane natywne adaptery. Jeśli web nie może spełnić kontraktu, recovery PRF dostępne tylko w bezpiecznych środowiskach.
- Obowiązkowy test wykonalności PRF: setup na jednym urządzeniu, zniszczenie lokalnego stanu, odzyskanie zsynchronizowanego poświadczenia na drugim urządzeniu (także zmiana platformy), identyczny wynik PRF dla tego samego salt, lokalne unwrap i odczyt oryginalnych danych. Macierz Linux/Windows/Android/iOS/web, dostawca/system/browser/native API, UV, sync/backup eligibility i rzeczywiste zachowanie po utracie urządzenia. Testy braku PRF, niezsynch. passkey, utraty PIN, revocation, błędnego credential, replay, niedozwolonego origin, sekretów w ruchu sieciowym, starego sejfu i rotacji. Nie oznaczaj device-bound passkey jako jedynej metody odpornej na utratę urządzenia. Zawsze obowiązkowy niezależny klucz recovery/PDF lub kod przechowywany poza GTMD i urządzeniem; PRF jest tylko opcjonalnym dodatkiem. Źródła: https://developers.google.com/identity/passkeys/supported-environments ; https://developer.apple.com/documentation/authenticationservices/asauthorizationpublickeycredentialprfassertioninput-swift.struct ; https://developers.yubico.com/WebAuthn/Concepts/PRF_Extension/Developers_Guide_to_PRF.html .
- IRecoveryProvider jako wspólna abstrakcja; WebAuthn PRF po zweryfikowaniu wykonalności, niezależnie od dostawcy. Nie implementuj Google Drive AppData, drive.file, OAuth dostępu do zewnętrznych dysków ani server-side escrow jako metod recovery; nie przechowuj sekretu w OIDC claims. Jeśli PRF nie działa na danej platformie/dostawcy, obowiązkowy niezależny klucz recovery nadal działa; nie zastępuj go integracją Drive. Google Password Manager może być dostawcą synchronizowanych passkeys, nie integracją Google Drive.

## 10. SMTP — tymczasowy transport w tym samym Git
Plany plus, pro i max: losowy alias przekierowania, wyłącznie nowe wiadomości; nie czytamy historii Gmail, bez Gmail OAuth. Współdzielony SMTP active-active, STARTTLS, publiczne MX/DNS/TLS. Backend widzi chwilowo plaintext w pamięci (nie identyczna gwarancja E2EE jak Syncthing), szyfruje pełny MIME z załącznikami hybrydowo dla zweryfikowanych publicznych kluczy klienta. Żadnego plaintext na trwałym dysku. Zapis envelope w gtm-mail tego samego repo, dual replication przed SMTP ACK.
Zaufana aplikacja pobiera/decrypt lokalnie, tworzy zadanie Markdown, załączniki, zachowuje pełne wymagane dane (w razie potrzeby oryginalny EML w main). Syncthing -> Git A -> Git B. Dopiero po zweryfikowaniu kompletnego importu i potwierdzeniu zapisania wymaganych plików w obu repo usuń transportową wiadomość z gtm-mail, także jej nieużywane historyczne obiekty. Sam commit delete nie zwalnia historii. Nie utrzymuj wiecznego oryginału w kolejce. Nie rozdzielaj repozytorium: zaprojektuj bezpieczne transakcje ref, cleanup/GC i locking w jednym Git, nie naruszając main, vault, tenant ani retencji. Zachowuj tylko małe trwałe potwierdzenia/dedupe (ogranicz retencję i koszty); identyfikatory i deterministic paths, nie obiecuj distributed exactly-once bez dowodu. Nie ufaj samemu ACK klienta. Obsłuż ponowienia SMTP, równoczesny import i odbiór, częściowy import, utratę jednej repliki, przekroczenie limitu main i offline urządzenia: wiadomość czeka bezpiecznie. Niezależne ograniczenia kolejki, liczby, rozmiaru, antyspam, retry z 4xx zamiast utraty maila; dotychczas 40 MiB raw i 100/dzień jako punkty wyjścia do walidacji. Weryfikuj pełne attachment/MIME roundtrip, rzeczywisty Gmail forwarding, mobilny import. Kolejka i techniczne potwierdzenia nie wchodzą do abonamentu; zaimportowane pliki main tak.

Nie naliczaj wielokrotnie tego samego obiektu. Nie wliczaj working tree jako dodatkowej kopii, drugiego Git, gtm-tenant, gtm-vault, gtm-mail, metadanych Git i technicznych danych Syncthing/GTMD. Wyłączenia muszą być weryfikowalne, użytkownik nie może ukryć arbitralnych plików pod technicznym prefiksem. Nie używaj du, fizycznej wielkości .git, bloków, packfile, kompresji. Wynik identyczny po repack, GC, zmianie dysku, replikacji przy tym samym zbiorze danych.
git rev-list + cat-file objectsize lub równoważna inkrementalna, odbudowywalna metryka, pełna niezależna weryfikacja. Zweryfikuj format receiveencrypted i deterministyczną wielkość oryginału bez zaufania do deklaracji klienta; jeżeli to nieweryfikowalne, jednoznaczny kontrakt logicznego rozmiaru zaszyfrowanej reprezentacji, jawny narzut. Nie zakładaj deduplikacji identycznej treści przed szyfrowaniem. Jednostki spójne (GiB).
Film 1 GB: ok. 3 GB fizycznie (working tree A, Git A/B), ok. 1 GB abonamentu. Po usunięciu z working tree ok. 2 GB fizycznie, nadal 1 GB abonamentu. Nowa odmienna wersja może dodać kolejne 1 GB. Podczas 7 dni ochrony nic nie odliczaj. Dopiero skuteczne bezpieczne usunięcie z historii obu kopii i chronionych ref zwalnia limit; bloby używane gdzie indziej pozostają.

## 12. BLOKER: selektywne ograniczanie przyrostu historii w Syncthing
Obecny kod nie pauzuje całego folderu przy limicie, ale NIE ma twardego ograniczenia przyrostu historii. Zbadaj Syncthing protokół i kod, admission control, ewentualny kontrolowany fork (open source, utrzymywalny). Przy pełnym limicie nadal działają download, odczyt historii, pobieranie starych wersji, usunięcia working tree i ich synchronizacja, zarządzanie historią, cancel, upgrade/gift. Blokuj wyłącznie przyrost rozliczanych danych, również modyfikacje istniejących plików. Nie używaj folder-wide pause, minDiskFree, samego filesystem quota ani okresowego pomiaru jako rozwiązania. Nie kasuj historii automatycznie.
Rezerwuj budżet dla operacji w toku, uwzględnij kilka urządzeń, złośliwego klienta, równoczesne modyfikacje dużych plików, wersje już obecne, błędy Git, awarie po przyjęciu danych i przed commitem, replikację, downgrade i koniec gift. Nie potwierdzaj zapisu, który nie może zostać utrwalony. Niezależna przestrzeń techniczna na metadane i niezbędne operacje. Przetestuj realny pełny filesystem, native usunięcia/download, awarie między etapami, nieprzekraczalność limitu.

Nazwa, ścieżka, rozszerzenie/ikona, logiczny rozmiar, daty, liczba wersji, data usunięcia, możliwe do odzyskania miejsce. ## 14. Ochrona przed ransomware i reautoryzacja
Zwykła zmiana/usunięcie pliku nigdy nie kasuje jego historii. Ransomware nie może zniszczyć oryginałów przez normalną synchronizację. Trwałe usunięcie wymaga **ponownego ręcznego wpisania aktualnego hasła GTMD** i weryfikacji po stronie serwera dla konkretnego żądania (nie sama sesja JWT, biometria, passkey ani przycisk potwierdzenia zamiast hasła). MFA/second factor w przyszłości, zaprojektuj rozszerzalność; nie uzależniaj MVP od wdrożenia MFA użytkownika przy purge. Panel administratora niezależnie wymaga MFA/SSO. Rate limit, krótko ważny challenge związany z operacją, ochrona przed replay/CSRF, nigdy loguj hasła. Rozważ ryzyko malware/keylogger i resetu hasła; samo hasło nie chroni przed kompromitacją endpointu. 
Żądanie purge, co najmniej 7 dni, anulowanie, hold administratora może tylko wydłużać okres, nie skracać; wszystkie stany trwale dual-replicated i autoryzowane. Przez okres ochronny miejsce nadal zajęte. UI pokazuje deadline i możliwość undo. Nie dopuszczaj usuwania przed terminem.

## 15. BLOKER: niezależna siedmiodniowa retencja odporna na administratora
Obecne API intent/7 dni/cancel/hold i offline purge candidate nie zapewniają rzeczywistej retencji ani live purge. Zbadaj provider-enforced immutability, chronione snapshoty, niezależną autoryzację destrukcji i rozdzielenie kompetencji. Przez 7 dni także zwykła eskalacja admina nie może usunąć chronionej kopii. Git deny-force-push, chmod/chattr, RBAC lub deadline nie są dowodem odporności na administratora/root. Rozwiąż konflikt dwóch pełnych kopii, jednego repo na klienta, braku S3/trzeciej pełnej kopii i niezależnej nieusuwalności. Jeżeli dostawcy nie pozwalają zapewnić wszystkich warunków, przedstaw konkretne ograniczenia i alternatywy do decyzji użytkownika; nie osłabiaj gwarancji po cichu. Wstrzymaj live purge do weryfikacji rzeczywistej ochrony, w tym break-glass i prób obejścia. 
Po terminie: atomowo sprawdź autoryzację/hold/cancel, fence writerów, przygotuj odizolowany kandydat historii, zweryfikuj zakres i wszystkie refs/objects (shared blobs, reflogi, tagi, protected refs), zachowaj pozostałe dane i gałęzie, bezpiecznie opublikuj obie kopie, sprawdź fsck/ref i integralność, GC tylko nieużywane dane; zwolnij limit po potwierdzeniu. Testy awarii w każdym momencie, w tym pomiędzy zmianą obu kopii, bezpieczne wznawianie/rollback w ramach ochrony. Stara replika nie może wskrzesić usuniętych danych. Bufor na operacje rewrite, nie dodatkowa stale działająca pełna kopia. Nie niszcz jedynej bezpiecznej repliki.

## 16. Współdzielone storage i autoscaling
Żadnego z góry opłacanego PVC 3x/5x planu każdego klienta. Pula współdzielonych fizycznych dysków z izolowanymi katalogami i uprawnieniami, kontener widzi tylko własne dane; XFS project quotas lub odpowiednik, twarde fizyczne limity niezależne od rozliczenia logicznego. Realne egzekwowanie CSI/filesystem (hostPath i deklaracja PVC nie wystarczają). Limity inode/IOPS/CPU/RAM, izolacja noisy neighbor, zapas Git/temporary/rewrite/restore/recovery. A i B niezależne nośniki/provider failure domains. 
Rzeczywista alokacja rośnie i maleje zgodnie z wykorzystaniem i prognozą. Początkowo >75% scale-up, >85% pilne i bezpieczne admission, <35% przez dłuższy czas konsolidacja/scale-down; progi konfigurowalne, histereza, tempo wzrostu, lead time, koszty. Zmniejszanie przez kontrolowaną konsolidację i zwolnienie zbędnych całych dysków/węzłów, nie shrink PVC. Weryfikuj integralność i dostępność wymaganych kopii przed usunięciem nośnika. Uwzględnij zapas na pełną odbudowę utraconej chmury. Testy izolacji i zapełnienia realnej puli. 

## 17. Active-active i automatyczny failover
Wszystkie współdzielone usługi redundantnie active-active obu cloudów, nie tylko cold standby. Ingress, API, SMTP, provisioning, monitoring i routing muszą przetrwać utratę jednego dostawcy. Przy utracie A odtwórz Syncthing, ten sam cert/key/Device ID, pełny Git, zaszyfrowany working tree z main, wszystkie gałęzie i konfigurację z B. Przy utracie B odtwórz Gitea/SQLite od zera, konta techniczne i uprawnienia, TLS, pełny Git z A. Odtwórz routing, service discovery, sekrety, przydział storage; nie wymagaj ręcznego SSH. Po powrocie chmury bezpieczna resynchronizacja i ponowne rozdzielenie kopii.
Rzeczywisty fencing/lease z niezależnym koordynatorem (dopuszczalny trzeci mały witness tylko metadane, nie dane klienta); quorum przy partycji, CAS, ochrona przed starymi instancjami, unikalność rejestracji, wersje konfiguracji i rollback. Nie traktuj manualnego FENCE_ACKNOWLEDGED jako automatycznego fencing. Ustal dostępność poszczególnych operacji gdy nie ma quorum lub dwóch zweryfikowanych replik; nie obiecuj jednocześnie nieograniczonych zapisów w partycji i silnej spójności. Obecne potwierdzenie Syncthing może poprzedzać Git commit/push (~12s pętla) — okno utraty najnowszych danych. Zbadaj ograniczenie lub wyeliminowanie; nie obiecuj RPO=0. Test RTO/RPO, utraty A/B, control plane, sieci, node/disk, stale replica, routing/DNS, niezależne recovery kluczy, capacity. Kompletne Terraform dwóch providerów i prywatne połączenia; Scaleway obecnie tylko walidowany moduł, nie realny dual-cloud.

## 18. Administrator i observability
