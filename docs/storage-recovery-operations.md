# Storage and recovery operations

## Storage budget (engineering preview)

The published plan is a live quota. Sync currently reserves 3× live quota and History 2× (new full-Git tenants). PR #10 uses a conservative working quota equal to effective plan + temporary gift, a history budget of 1.8× that quota (90% of the nominal history PVC) and a local disk reserve. It counts apparent encrypted working-tree bytes, allocated local Git/recovery bytes including unreachable objects and legacy LFS, and filesystem free space. It rejects new mail with HTTP 507 internally before committing if the projected history/free-space budget would be exceeded. Retries of already committed mail may replicate without admitting new bytes. The SMTP gateway returns a temporary failure, not success.

The private meter is reconciled at most once per minute per tenant under the existing controller. The folder is paused above budget, never purged. A paused folder cannot distinguish upload from deletion using Syncthing's native API; an operator can grant a temporary free allowance to allow the user to synchronize deletions. The controller does not have shell access for this operation. A failed measurement pauses rather than silently admitting unlimited writes. This is sampled backpressure, not hard quota: in-flight writes can overshoot; real per-volume CSI limits and B-side capacity monitoring must be validated. Encrypted representations and Git packing consume different bytes from plaintext. The current 1.8× budget is an explicit conservative implementation choice, subject to cost/load validation.

## Shared encrypted Control Plane backups

The optional **shared** state-backup container (not a third per-tenant container) uses Python SQLite online backup for accounts.sqlite and tenants.sqlite, copies only explicitly mounted configuration secrets, creates a SHA-256 manifest and streams a tar archive to age for two independent public recipients. Plain snapshots are on a memory-backed scratch volume in Helm; no plaintext archive is written to persistent volumes. Each database is internally consistent; the pair is not an atomic distributed transaction. Backup does not contain all tenant data (already in both Git archives).

Configure stateBackup.enabled, image, existingSecret and recovery.ageRecipient. The Secret must contain endpoint-a, endpoint-b (different HTTPS S3-compatible endpoints), bucket-a, bucket-b, credentials (AWS credentials profiles cloud-a and cloud-b, scoped to backup prefix Put/Get only), config (matching profile regions). Keep private age identities and break-glass credentials outside both workload deployments. Use distinct provider accounts, restricted credentials, independent retention/versioning, and avoid granting delete access to the writer. The worker uploads timestamped encrypted objects to both providers and downloads/verifies both checksums before reporting success. Readiness becomes false when no recent dual success exists (three intervals). Size scratch and memory limits for both DB snapshots and ciphertext; no production load test yet. Do not put credentials in Git.

For an authorized, independently fenced outage, download the selected encrypted snapshot from the surviving provider, run the backup image's restore command with --bundle, --identity, --target (nonexistent directory) and --scratch (RAM-backed). The restore verifies manifest and SQLite quick_check, refuses live overwrite, and writes a fresh staged directory including explicitly backed-up secrets. A separate recovery identity must restore Kubernetes Secrets, mount fresh volumes, reconcile tenant state and Stripe events, then enable routing. Periodic backup RPO is at least one interval plus outage/transfer duration; no RPO-zero claim.

## History purge candidate

The offline tool scripts/recovery/prepare-history-purge.py builds an isolated mirror with no push configuration and never mutates source refs or objects. It requires a literal relative opaque filename; a main path must already be removed from the live snapshot. Mail targets must match the exact .gtmd/inbox/<digest>.json shape. It rewrites only the selected data branch, verifies the historical path is not reachable from any remaining ref, verifies unrelated refs, preserves shared blobs used elsewhere, and garbage-collects unreachable bytes **only in the candidate**.

This tool cannot authorize a live purge. A separately enforced immutable retention service must protect the original history, serialize hold and cancellation decisions, validate the current request/deadline, fence both writers, verify both current refs, stage both copies, publish and verify both new refs, and retire/GC old storage only after the protection deadline. Neither a manual timestamp nor the offline tool is sufficient. No destructive production workflow is enabled.
